## 1. Phạm vi và cách đọc

### Cập nhật ảnh hành trình và player (09/10/2026)

**[FE]** `TimelineEvent` trong `src/types/domain.ts` có thêm `images?: ManagedImage[]` (`src`, `display?: {fit,x,y}`). Admin dùng `pages/admin/TimelineImagesEditor.tsx` để thêm nhiều ảnh vào từng mốc, tải file/chọn thư viện, thay/gỡ và chỉnh vùng hiển thị; `ProductEditor.tsx` lưu cùng aggregate sản phẩm. Gỡ ảnh khỏi mốc không xóa file thư viện. Save bị khóa khi upload đang chạy.

**[ĐX] D1:** bổ sung `timeline_event_assets(event_id TEXT NOT NULL REFERENCES timeline_events(id) ON DELETE CASCADE, asset_id TEXT NOT NULL REFERENCES assets(id) ON DELETE RESTRICT, position INTEGER NOT NULL CHECK(position>=0), fit TEXT NOT NULL CHECK(fit IN ('cover','contain')), x REAL NOT NULL CHECK(x BETWEEN 0 AND 100), y REAL NOT NULL CHECK(y BETWEEN 0 AND 100), PRIMARY KEY(event_id,position))`. Thêm index `timeline_event_assets(asset_id)` để kiểm tra reference khi xóa file. Không lưu binary/URL local trong D1. Thứ tự ảnh riêng cho từng mốc; một asset có thể được dùng lại trong nhiều mốc, framing riêng cho mỗi placement. Khi thay aggregate cần xóa association cũ trước khi thay `timeline_events`; thực hiện cùng transaction và revision check của product.

**[ĐX] API:** dùng các endpoint upload/list/read/delete media và create/update product đã mô tả ở dưới; không cần endpoint upload riêng cho timeline. `ProductWrite.timeline[].images` là `[{assetId,display?:{fit,x,y}}]`; `ProductDTO.timeline[].images` là `[{src,display}]` với URL đọc được theo quyền. Admin detail cung cấp ID ảnh trong metadata `media.timeline` theo event/position để adapter ánh xạ lại Write. Kiểm tra asset thuộc bucket MEDIA, kind=image, state=ready, quyền admin, reference còn tồn tại; reject file internal, video/document hoặc asset deleting. Đề xuất cap 20 ảnh/mốc (cần xác nhận và đo, không phải luật từ mock). Public chỉ trả ảnh gắn sản phẩm published, variants thumbnail thích hợp; không expose object key/internal file. Asset delete trả 409 nếu còn được timeline tham chiếu; publish/unpublish/gỡ ảnh phải invalidate cache của product và file association tương ứng.

**[FE] UI thuần client:** header sticky, sidebar thu gọn/kéo rộng lưu localStorage `hytales.sidebar.width` và `.collapsed`; không cần database hoặc auth API mới. ## 3. Kiến trúc và công nghệ

**[YC] Stack cố định:** Cloudflare Workers chạy Hono/TypeScript, Cloudflare D1 lưu dữ liệu quan hệ và metadata, Cloudflare R2 lưu binary. Không dùng filesystem máy chạy Worker làm kho bền vững.

**[ĐX] Triển khai một origin:** Worker phục vụ frontend build bằng Static Assets và API `/api/*`; `/q/*` chạy resolver ở Worker; `/p/*`, `/admin/*` và trang chủ dùng SPA fallback. Cookie admin cùng origin giúp giảm cấu hình cross-site. Cấu hình `assets.directory = "../front_end/dist"`, binding `ASSETS`, `not_found_handling = "single-page-application"`, `run_worker_first = ["/api/*", "/q/*"]`. API 404 luôn trả JSON, không trả index.html. Đối chiếu cấu hình với [Workers SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/) khi triển khai.

Luồng: Browser → Worker/Hono → validation/auth/service → D1; binary → R2 qua binding và response stream. Có 2 bucket **private ở cấp bucket**:

- `MEDIA`: ảnh/phim nguồn, variants, file public đã duyệt, media draft/quarantine. Public truy cập qua Worker kiểm tra trạng thái và association, không mở cả bucket.
- `INTERNAL_FILES`: hồ sơ nội bộ, tài liệu đính kèm. Chỉ admin được đọc. Không bật public `r2.dev` hoặc public custom domain cho bucket này.

Hono xử lý routes/middleware; Zod (hoặc schema tương đương có kiểm thử) kiểm tra runtime; D1 prepared statements + SQL migrations; không bắt buộc ORM. Pin version và commit lockfile. Công cụ phát triển đề xuất Node 24, Wrangler 4 tương thích, TypeScript, Vitest Workers pool/Miniflare cho D1/R2 và Playwright cho frontend. `compatibility_date` ban đầu `2026-10-09`, kiểm tra thư viện trong workerd thật; không giả định npm Node APIs đều có trên Worker.

Xử lý ảnh: tạo AVIF/WebP/thumbnail bằng pipeline offline đáng tin cậy hoặc **Cloudflare Images binding nếu được duyệt chi phí**. Binding này là capability riêng, không mặc định nằm trong R2/D1. Worker không tự có Sharp/FFmpeg native. Video cần pipeline kiểm tra codec, tạo poster và bản xem trước; có thể chạy công cụ offline lúc import hoặc một processor riêng sau này. Chỉ cho publish media đã xử lý xong. [Cloudflare Images binding](https://developers.cloudflare.com/images/optimization/binding/) hỗ trợ biến đổi ảnh nhưng vẫn cần thiết kế cache và ngân sách.

Tunnel localhost đang dùng chỉ là preview frontend, URL có thể đổi và máy phải online. Không dùng URL tunnel làm domain QR in thật hoặc storage production. Production cần Cloudflare account, domain và HTTPS ổn định đã xác nhận.

## 4. Thiết kế database D1

Toàn bộ schema sau là **[ĐX]**. SQLite: ID/key/string/JSON là `TEXT`, timestamp là ISO UTC `TEXT`, boolean `INTEGER CHECK IN (0,1)`, số nguyên `INTEGER`, quantity `REAL`. Các trường ghi `?` cho phép NULL. Timestamps do server tạo. ID mới là UUID, nhưng import phải giữ ID seed như `nhan-long` để QR cũ còn hoạt động; không ép ID legacy thành UUID. Ngày sản xuất/HSD dùng `YYYY-MM-DD` hoặc NULL; DTO đọc chuyển NULL về `""` để phù hợp FE.

Dùng foreign keys, NOT NULL/CHECK/UNIQUE phù hợp. D1 hỗ trợ quan hệ FK; tham khảo [D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/). Không lưu Blob, bytes ảnh/video/tài liệu hoặc base64 trong D1. JSON nội dung có cấu trúc nhỏ (facts/blocks/framing) là dữ liệu nghiệp vụ, không phải binary file.

CAS không đổi row thì children cũng không được đổi; đọc kết quả trả 409. Một UPDATE ảnh hưởng 0 row không tự là lỗi SQL/rollback. Phải test conflict không mất timeline/FAQ/media; constraint error trong children phải rollback toàn aggregate. Có thể chọn giải pháp transaction khác đã chứng minh tương đương, ghi rõ trong implementation docs.

Scoped FAQ và QR mutation cũng phải tăng revision của parent Product/Settings trong cùng batch. `revision` trả về từ endpoint FAQ là revision aggregate parent dùng cho If-Match; counter của quick_reply_sets chỉ phục vụ nội bộ. ProductEditor hiện có editor FAQ trong tab Khối & hỏi đáp, nên full ProductWrite vẫn có thể thay FAQ; SettingsWrite cũng có thể thay bộ chung. Khi FAQ được sửa ở trang riêng, editor aggregate cũ phải nhận409 thay vì ghi đè nó. Áp dụng tương tự với QR destination; endpoint dedicated tránh gửi full product nhưng vẫn làm invalid parent revision.

## 5. Quy ước API và DTO

Prefix `/api`, HTTPS production, UTF-8. Detail trả object trực tiếp, list mới trả `Page<T> = {items:T[], nextCursor:string|null, total?:number}`. **Đây là thay đổi so với FE đang mong array**, cần sửa adapter/callers ở mục 10, không chỉ bật env. Limit mặc định public 6, admin 20; max 100, media 24; cursors opaque được validate/bind filter, keyset theo `(sort_order,id)` cho cards và `(created_at,id)` cho inbox. Không download toàn list rồi slice trong browser.

`ProductDTO` giữ toàn bộ field trong `domain.ts`: id, slug, name/nameEn, subtitle/region/season/story VI/EN, image/video/gallery URLs, imageDisplay/galleryDisplays, transcript, facts, batchCode, orderUnit, harvestedAt/expiresAt, certifications, timeline, faq, blocks, status, demo, qrDestination. Bổ sung `revision`, `media` metadata IDs/variants cần thiết. Public projection chỉ record published, không có admin IDs/audit/internal attachments/object keys/bucket. Không gửi toàn transcript/gallery trong cards.

`ProductCardDTO` tối thiểu: id, slug, name/nameEn, subtitle, region, season, image, imageDisplay, card image variants/dimensions, hasVideo, demo. `ProductWrite` dùng các field nội dung Product và `coverAssetId`, `videoAssetId?`, `gallery:[{assetId,display?}]`; không nhận URL/data URL/`local-media:` tự do làm quyền sở hữu file. `media` trong admin detail cung cấp các ID để editor chuyển sang ProductWrite. Server quyết định id/slug/timestamps/revision; create không tin ID/batchCode do browser nếu cần tự sinh, nhưng cho phép batchCode do admin sửa sau validation.

ProductWrite cụ thể gồm name/nameEn, subtitle/region/season/story, transcript, facts, batchCode tùy chọn khi create, orderUnit, harvestedAt/expiresAt, certifications, timeline, faq, blocks, status, demo, coverAssetId/imageDisplay, videoAssetId và gallery placements. Không ghi id/slug/revision/createdAt/updatedAt hoặc qrDestination từ body; QR dùng endpoint riêng. POST create có thể tạo draft thiếu media; publish phải qua điều kiện ở mục8. Unknown fields trong input production bị từ chối hoặc lọc bằng schema được test, không spread request body thẳng vào SQL.

SettingsDTO giữ organization/email/zaloUrl/socialWidgetEnabled/chatGreeting/quickReplies/brandLogo/storyImages/imageDisplays như FE. Admin SettingsWrite thay reference URL bằng asset ID + display; public DTO chỉ tham chiếu assets ready/public. Social links chưa cấu hình vẫn có thể có URL trống. Review/Inquiry/Message trả field đang có trong domain, cộng moderation/consent metadata chỉ trong admin projection. MediaAssetDTO mở rộng `{id,name,kind,url,poster?,state,visibility,mimeType,sizeBytes,width?,height?,variants?}`; internal file chỉ có admin download URL, không public url.

Lỗi thống nhất, tương thích `data.message` FE hiện tại:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Vui lòng nhập số điện thoại hợp lệ.",
  "fieldErrors": { "phone": "Cần 9–15 chữ số." },
  "requestId": "..."
}
```

Các mã chính: 400 query/cursor/JSON sai; 401 chưa đăng nhập; 403 quyền/origin/CSRF sai; 404 record/file không có hoặc không được public; 409 version/duplicate/reference/conflicting idempotency; 413 quá dung lượng; 415 MIME không hỗ trợ; 422 field/nghiệp vụ không hợp lệ; 429 limit + Retry-After; 500/503 lỗi hạ tầng đã redact. JSON body cap đề xuất 256 KiB; không áp dụng cap này cho endpoint binary. Responses admin/auth/private `Cache-Control: no-store`.

## 6. Upload, đọc và xóa file

### 6.1 Chính sách file

| Purpose                   | Loại cho phép | Giới hạn                                              | Visibility mặc định                                                             |
| ------------------------- | ------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| product/site/social image | JPEG/PNG/WebP | 12 MiB [FE]; đề xuất ≤40 megapixel và không animation | Quarantine/processing → public-ready khi duyệt + được gắn vào nội dung xuất bản |

| product video             | MP4/WebM      | 300 MiB [FE], chunk upload                            | Processing; bản preview public sau kiểm tra codec/metadata                      |
| internal document         | PDF           | 10 MiB [ĐX]                                           | Internal, chỉ admin                                                             |
| QR logo phiên xuất        | JPEG/PNG/WebP | 512 KiB [FE]                                          | Frontend xử lý cục bộ; không cần lưu backend nếu chưa thêm mẫu QR persistent    |

[?] DOCX/XLSX hoặc loại tài liệu khác chưa được frontend yêu cầu; mặc định từ chối cho đến khi thêm parser/giới hạn ZIP decompression và chính sách malware. SVG/HTML/JS/executable không nhận qua upload công khai. Static logo/SVG placeholder tin cậy của frontend vẫn phục vụ như build asset, không phải file do khách tải.

Kiểm tra extension chỉ là gợi ý; đối chiếu MIME khai báo với magic bytes, dimensions/codec qua parser đáng tin cậy. Đếm bytes thực tế kể cả khi thiếu/sai Content-Length, stop stream vượt limit. Hash checksum để integrity, không dùng checksum client làm chứng cứ file an toàn. Tên gốc sanitize độ dài; object key server sinh `purpose/uuid/version.ext`, không để tên người dùng trở thành path. File chưa qua validation không có public read. Thiết lập `X-Content-Type-Options:nosniff`; PDF internal dùng `Content-Disposition:attachment` và tên đã escape; internal no-store. Image pipeline loại EXIF/location và tạo derivatives; original internal/admin-only nếu còn metadata nhạy cảm. Virus scanning tài liệu nếu chưa có thì giữ quarantine và không cho publish; MVP internal PDF cần parser/scan policy được chọn rõ.

### 6.2 Luồng upload và xử lý

1. Xác thực admin hoặc review ticket scope; rate limit, kiểm tra purpose/type/declared size/quota, tạo asset pending và upload job. Không cho guest chiếm object key của admin.
2. File nhỏ: giới hạn trước parse multipart, tránh giữ nhiều bản buffer 12 MiB trong RAM; kiểm tra header và stream/tee có cap. Video 300 MiB: **không gửi một request/buffer nguyên file**; dùng R2 multipart 8 MiB/part, tối đa 2 part đồng thời, part cuối có thể nhỏ hơn. Kiểm tra platform limits tại triển khai: Workers có giới hạn memory/request body tùy môi trường; [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) và [R2 multipart Workers](https://developers.cloudflare.com/r2/api/workers/workers-multipart-usage/).
3. D1 track ETag/byte count từng part; complete chỉ danh sách liên tiếp, đủ size, không lặp và đúng owner/job. Dùng ETag lưu server, không tin list giả client. Re-complete idempotent; expired ticket/job trả410; đề xuất TTL job 24h, ticket review 10 phút.
4. R2 complete → head xác minh final size/type + thực hiện kiểm tra file/pipeline. D1 asset processing, chưa public. CPU codec/transform nặng do processor đã chọn thực hiện; Worker header validation không chứng minh video có codec phát được. Chưa có processor video thì chỉ import các preview đã kiểm tra offline, không bật arbitrary video publish.
5. Pipeline ghi variants trong R2, cập nhật D1 metadata thành ready; FE polling trạng thái và chỉ chọn asset ready. Failure chuyển rejected, nêu lỗi có thể sửa; retry không nhân đôi object. Admin public content chỉ sử dụng assets được duyệt purpose public, internal không thể chuyển public bằng sửa URL.
6. D1 và R2 không atomic cùng nhau: ghi trạng thái/job trước, R2 sau, final metadata sau. Scheduled cleanup retry asset deleting, abort expired multipart và xóa orphan sau grace period đề xuất 24h. Ghi audit và không xóa object đang có references. Không chỉ dùng `waitUntil` như hàng đợi bền vững; jobs D1 phải cho phép resume/retry.

MVP proxy chunk bằng R2 Workers binding, **không cần S3 access key trong frontend**. Nếu sau này dùng presigned direct upload để giảm traffic Worker, đó là thay đổi có chủ đích: kiểm tra quyền/purpose trước ký, expiry ngắn, key server tạo, CORS exact origin và complete/head/scan trước ready. Signed URL là bearer credential; chỉ S3 endpoint, không giả định hoạt động với public custom domain. Xem [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

### 6.3 Đọc và xóa

Public read mỗi lần kiểm tra asset ready/public và ít nhất một published association: product published, review published, hoặc site/social config công khai. Asset chỉ nằm thư viện/draft không public. Public endpoint không serve original nội bộ/quarantine, không suy variant/key từ path tùy ý. Admin preview dùng cookie và endpoint admin riêng. Internal document không có URL share tự do trong MVP; download kiểm tra admin trên mỗi request, không dùng public cache.

Video có `Accept-Ranges:bytes`, validate một Range, trả206/Content-Range/Content-Length; unsatisfiable416; HEAD không tải body, conditional ETag/304 cho public variant. Dùng R2 stream để không buffer cả phim; tham khảo [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). Range preview bỏ qua shared full-object cache nếu chưa có chiến lược kiểm thử đúng.

Gỡ cover/gallery/logo chỉ xóa association; file vẫn trong library như FE hiện tại. DELETE asset: transaction kiểm tra mọi reference → nếu còn dùng trả409, không force-delete làm hỏng nội dung; nếu không, mark deleting → xóa original + variants R2 → mark deleted/tombstone. R2 lỗi giữ deleting để cron retry, không trả đã xóa thành công khi object chưa xóa. Chặn association mới vào deleting. Unpublish/delete product ngừng public access/QR ngay theo D1 gate; không tự xóa snapshot/history. File đã được người khác download trước đó không thể thu hồi từ thiết bị của họ.

## 7. Xác thực, phân quyền và an toàn

**[ĐX] Session server-side:** bootstrap admin bằng CLI riêng, không public register và không mật khẩu demo. Email/password login giữ UI hiện có. Password dùng KDF chuẩn có salt ngẫu nhiên, encoded params/version; đề xuất `scrypt` qua implementation tương thích Workers, cấu hình tối thiểu được đánh giá như N=32768,r=8,p=3, dkLen=32, salt16+ bytes. Benchmark CPU/memory trên Worker staging trước bật production, giới hạn số login hash đồng thời; không hạ cost tùy tiện để vừa free plan. Nếu không đáp ứng được thì dùng identity provider được duyệt và cập nhật UI/adapter. Căn cứ: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), implementation tham khảo [noble-hashes scrypt](https://github.com/paulmillr/noble-hashes). Pin/test package và test vectors; không dùng benchmark máy dev như bằng chứng Workers đáp ứng.

Session token 32 random bytes, D1 chỉ SHA-256 token; cookie production `__Host-hytales_admin; HttpOnly; Secure; SameSite=Lax; Path=/`, không Domain. TTL đề xuất 8h absolute; rotate khi login, revoke logout/admin disabled; không lưu bearer token localStorage. Dev HTTP dùng cookie name riêng không Secure, không tái sử dụng cấu hình này production. `/auth/me` kiểm tra hash/expiry/active/role, public không cần cookie để đọc nội dung.

Tất cả mutation admin kiểm tra exact trusted Origin + session-bound CSRF header; login dùng pre-auth CSRF cùng origin. JSON PUT/PATCH/DELETE, multipart và binary chunk đều phải được bảo vệ. Hono CSRF mặc định tập trung một số form MIME, vì vậy không chỉ bật middleware rồi mặc định JSON đã được kiểm tra. Xem [Hono CSRF](https://hono.dev/docs/middleware/builtin/csrf). Reject invalid Origin/CSRF trước upload bytes. CORS nếu dev khác origin chỉ exact allowlist + credentials, không `*`; cùng-origin production vẫn kiểm tra CSRF. Có thể không nhận Origin cho GET/HEAD, mutation browser phải có origin hợp lệ.

Anonymous forms dùng validation, honeypot tùy chọn, Turnstile server verification (site action/hostname đúng) và rate limits. Đề xuất login 5 lần/phút/IP, forms 5/phút/IP và giới hạn theo product/visitor, upload 2 jobs đồng thời/admin; threshold cấu hình và đo tránh khóa nhầm người dùng 4G chung NAT. Rate limiting binding có scope riêng, không giả định counter tuyệt đối toàn cầu. Không dùng dữ liệu IP để profiling dài hạn. HTTP server từ chối injection, prepared SQL, plain text render, sanitize file names, không fetch URL ngoài để import file (SSRF).

Không log password/cookie/CSRF/ticket/phone/full message. Audit thay đổi admin với request ID; RBAC server ở mọi endpoint, test direct API khi không có guard UI. Không cần visitor account chỉ để gửi form.

## 9. Cache, phân trang và mục tiêu hiệu năng

**[YC] Mục tiêu:** nội dung chính dưới **2,0 giây**, không coi stack bảo đảm tốc độ. Định nghĩa nghiệm thu [ĐX]: trang `/` và ít nhất ba `/p/:slug` đã publish, thời điểm từ navigation start đến heading + nội dung tóm tắt + CTA có thể dùng + hero/poster chính hiện đủ; đồng thời LCP p75 <2,0s. Playback video không phải điều kiện kết thúc, nhưng bytes autoplay cạnh tranh mạng phải được tính trong phép đo cấu hình mặc định.

### Điều kiện kiểm thử phải ghi trong báo cáo

- Lab production build, HTTPS domain staging/prod tại VN, Android tầm trung viewport390×844, Chrome stable ghi rõ version, CPU throttle4×, network profile explicit down9Mbps/up1.5Mbps/RTT150ms. Lab là mô phỏng, không gọi là 4G thực tế.
- Field: tối thiểu một Android tầm trung và một iPhone thật, Wi-Fi tắt, SIM 4G của ít nhất hai nhà mạng ở VN; ghi model/OS/browser/nhà mạng/địa điểm/thời gian/signal, down/up/RTT đo gần lượt test. Báo test nếu băng thông/RTT khác profile; không loại lượt xấu tùy ý để đạt mục tiêu.
- Mỗi route/thiết bị/mạng tối thiểu20 lượt fresh-navigation cold browser cache; thêm20 warm cache, báo riêng cold/warm và trạng thái edge hit/miss, không dùng warm thay cold. Cold browser không đồng nghĩa cold Cloudflare edge; muốn đo edge miss cần version/test URL riêng và ghi nhận headers. Ghi p50/p75/p95, số lỗi, raw traces/video + Web Vitals. Nếu chưa có thiết bị/4G thì đánh dấu **chưa nghiệm thu**, không dùng Lighthouse desktop để xác nhận.
- Dataset: ít nhất20 sản phẩm,50 ảnh, ba preview phim,1000 reviews/inquiries/messages và100.000 QR aggregates/events kiểm thử; ghi rõ load đồng thời đề xuất10 khách và2 admin. Không đưa fixture giả vào production. [ĐX] CLS≤0,1, INP p75≤200ms, public API TTFB p75≤300ms trong profile xác định; đây là ngân sách phụ, không thay tiêu chí2s.

### Kế hoạch tối ưu có đo

1. `/bootstrap` một request public nhỏ lấy settings/cards/hero metadata, parallel hóa cần thiết; dùng shared query cache để AppearanceProvider/Layout/SocialWidgets/ChatWidget không fetch settings lặp. Product detail tải một object theo slug, reviews/related gallery dưới fold độc lập, lỗi review không làm mất câu chuyện.
2. First page cards6 record, keyset phân trang; slider tải trang kế khi gần cuối hoặc nút “Xem thêm”, có loading/retry, không tự accumulate toàn catalog ngay mount. Options picker tìm kiếm/phân trang + fetch selected ID, không mất product thứ20 vì chỉ có6cards. Admin summaries bằng SQL, inbox/media từng trang.
3. Ảnh: responsive `srcset`320/640/960/1440, explicit width/height/aspect ratio; hero poster fetchpriority high/eager, card/gallery dưới fold lazy và async decoding. Target hero mobile≤150KiB, card thumb≤60KiB, bootstrap≤40KiB compressed, initial critical transfer≤400KiB (không video), first JS≤180KiB compressed [ĐX] rồi đo. Framing fit/x/y giữ nhất quán across variants, chưa overwrite originals.
4. Hero film: ưu tiên poster/main content trước; chỉ nạp video đang hiển thị, preload none/metadata theo đo, tôn trọng saveData/reducedMotion, tạm dừng ngoài viewport/hidden tab như FE. Đề xuất trì hoãn autoplay cho đến critical content render; nếu vẫn vượt budget trên4G cân nhắc click-to-play mặc định cần ghi decision UX, không quảng cáo có autoplay mà bỏ silently. Preview adaptive độ phân giải/bitrate720p hoặc480p, faststart, Range; không gửi video gốc200–300MiB lúc tải trang.
5. Lazy route chunk admin; tải `jspdf/qrcode` khi mở QR/export, tránh vào public bundle. Self-host font WOFF2 subset VI/EN đủ dấu, font-display swap, preload tối đa font critical. Static build assets có content hash cache long immutable; index HTML short revalidation để không trỏ JS cũ đã xóa.
6. Public JSON dùng ETag/revision, client stale-time đề xuất30s cho nội dung không nhạy cảm; publication gate luôn đọc status/deleted state trước phục vụ cached product. Shared edge response cache có key revision lấy sau gate, TTL60s; sửa Settings/Product đổi revision để cache cũ không được chọn. Không cache draft/admin/auth/inbox/internal/review pending. Với public reviews moderation gate kiểm tra trước cache, hoặc MVP no-cache với index cho tới đo.
7. Public media Worker check asset+published association **trước** lấy bytes từ edge cache; key gồm asset version/variant, cached bytes không chứa cookie. Browser Cache-Control max-age đề xuất300s cho public variants; cần thu hồi tức thì khỏi browser đã cache thì chọn no-cache/revalidate thay vì hứa có thể thu hồi. Internal no-store, không dùng public immutable CDN. Chỉ approved non-revocable static build assets dùng1year immutable. `cache.delete` trên Worker chỉ tác động cache ở data center đang gọi, không mặc định purge toàn cầu; revision gate hoặc Cloudflare purge đúng phạm vi là bắt buộc. Căn cứ [Workers Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).
8. Index, SELECT projection, LIMIT keyset, không N+1 query/gallery per card, D1 batch nhiều reads khi có lợi, instrument Server-Timing DB/cache/R2/total (không lộ secret). Đo rows read/query và Worker CPU; không thêm KV/replicas/batching không cần thiết trước profiling. Mutation quan trọng read-after-write không được hiển thị phiên bản cũ do cache/read replica.

Nếu LCP/content p75≥2s: báo bottleneck cụ thể và chưa đạt; giảm tải critical/media/request waterfall, đo lại cùng profile. Có thể cân nhắc server bootstrap HTML/SSG cho landing nếu JS/data waterfall vẫn là bottleneck; đây là bước tối ưu sau số đo, không bắt buộc rewrite framework.

```powershell
# Từ front_end_codex/backend — chỉ dùng sau khi các file/scripts đã được triển khai

npx wrangler d1 migrations apply DB --local
npm run seed:local

# Terminal khác, từ front_end_codex/front_end

```

Để production same-origin: build frontend trước, Worker Static Assets trỏ dist, không đổi working directory tùy tiện. Chỉ deploy staging sau tests. D1 remote migration/import/deploy production thay đổi external state: kiểm tra đúng account/env/domain, backup và quyền của chủ dự án trước khi chạy. Tham khảo [Wrangler D1 migrations](https://developers.cloudflare.com/workers/wrangler/commands/d1/). Không dùng tài khoản demo hoặc fixture PII trong production.

Backup/restore: export D1 theo quy trình account, giữ phiên bản migrations; R2 originals/versioned keys + manifest D1 reference; test restore staging cả record và object. Retention/chi phí/chế độ versioning cần xác nhận. Worker rollback code không rollback D1 migration hay mất file đã xóa; migrations nên additive/backward compatible, destructive cleanup sau grace period.

## 12. Thứ tự triển khai và tiêu chí hoàn thành

AI tiếp theo có thể bắt đầu local từ bước1. Không cần lịch sử chat; đọc các source paths mục2 để kiểm tra frontend chưa đổi tiếp. Các acceptance dưới đây là yêu cầu kiểm chứng, không phải kết quả đã đạt.

- [ ] **Bước 1 — scaffold và contract.** Tạo backend tree, package/lock/tsconfig/wrangler, env validator, Hono health/error/requestID; OpenAPI cho DTO/API trên. - [ ] **Bước 3 — admin auth.** Password KDF benchmark/test vectors, bootstrap CLI, session/cookies/CSRF/origin/rate-limit/login/logout/me.
